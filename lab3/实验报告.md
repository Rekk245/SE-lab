## 1. 实验目的与实现范围

本次实验延续实验一《多人共享记账系统需求规格说明书》和实验二的软件设计。目标是把 UML 中的账本、成员、收支审批、入账、分摊和结算关系实现为可运行程序，使用构建工具生成运行包，并通过 Git 管理本地和远程代码。

## 2. 从 UML 到代码

### 2.1 分层与模块映射

实现保留了实验二“表现层—业务服务层—数据访问层”的职责划分。界面负责收集输入与显示结果，权限和金额检查统一在服务层执行，数据库层处理事务与关联约束。按钮是否可用不是授权依据；即使绕过界面调用服务，也会重新查询当前账本成员角色。

| UML 对象或组件 | 代码与存储映射 |
| --- | --- |
| User、Ledger、Membership | `auth.py`、`membership.py`；users、ledgers、memberships、invitations 表 |
| Transaction、Expense、Income | `domain.py` 的不可变数据类；transactions 表按 direction 区分子类型；`QueryService.model()` 构造对应对象快照 |
| Evidence、Review | evidence、reviews 表；`workflow.py` 与 `base.py` 记录报价引用和被审核内容版本 |
| JournalEntry、PostingService | journal_entries 表及 `posting.py`；POST/REVERSAL 分别唯一 |
| Share、Payment、Obligation | shares、payments、obligations 表；完成支出时在同一事务中产生 |
| OfflineSettlement、SettlementAllocation | settlements、allocations 表；`settlement.py` 登记实际线下款项 |
| Budget、查询统计组件 | budgets 表及 `query.py`；只汇总有效入账效果 |
| AuditEvent、RequestReceipt | audit_events、request_receipts 表；与业务成功结果共同提交 |

并非每个 UML 类都机械地对应一个带有增删改查方法的 Python 类。纯关系对象映射为数据库表，领域值与收支快照使用数据类，有跨对象一致性要求的行为放入业务服务，避免在多个对象中分别提交事务。

### 2.2 状态图映射

支出正常流转如下：

```text
提交支出 → APPLICATION（申请）
申请批准 → PURCHASE（购买）
登记与获批金额一致的付款 → 仍处于 PURCHASE
申请人确认使用 → USED（已经使用）
完成审核通过 → COMPLETED（完成）+ 唯一入账
```

申请批准不产生费用，登记付款和确认使用也不产生实际统计。只有完成审核成功提交后，总支出才增加。

修改金额、模式或名单时，增加 `content_version`，清空批准金额及批准内容版本，退回申请。后续付款和完成同时检查批准金额、实际金额与内容版本，旧批准结果不能授权新内容。

申请审核驳回后进入 REJECTED，可修改重提；完成审核驳回的支出保持 USED，保存驳回原因。主动撤销进入 CANCELLED。已完成记录不能当作未完成申请直接修改或撤销，只能由最高管理员通过作废和更正处理。

收入使用 PENDING → COMPLETED，不套用购买与使用阶段。

### 2.3 活动图与时序图映射

`PostingService.complete(transaction_id, version, request_id)` 对应实验二完成审核时序图：

1. 开启 SQLite 写事务，查询真实所属账本与当前成员角色。
2. 检查审核权限及普通管理员不得自审的约束。
3. 查询请求回执；同一请求、同一内容返回原入账 ID，同标识不同内容报冲突。
4. 校验显示版本、当前阶段、获批金额、付款金额、内容版本与退款状态。
5. 写审核记录、完成状态和唯一 POST 入账。
6. 对支出生成分摊份额及应结债务，写操作日志和请求回执。
7. 整体提交。任何一步异常都回滚，不保留半完成结果。

SQLite 与原设计的实现机制不同，但仍保留“先校验，状态与财务效果同事务提交”的顺序。数据库还通过外键、非负/范围检查以及 `(transaction_id, kind)` 唯一约束提供第二层保护。

### 2.4 金额、分摊与结算

输入金额由十进制字符串转为整数分，拒绝空值、非数字、负数、零、超过两位小数和超出上限的金额。范围 0.01～99,999,999.99 元是本次采用的候选规则，不是新增的甲方确认事实。

均摊按成员 ID 稳定升序处理余数。例如 100 元由三人分摊，得到 33.34、33.33、33.33 元，合计严格为 100 元。所选成员必须属于账本，不能重复；实际付款人不必是均摊参与者。

团队支出由成员垫付时，生成“团队 → 垫付成员”的债务；团队直接付款不形成报销债务。均摊时，其他参与者向实际垫付人承担各自份额。线下结清只写 settlements 和 allocations 并减少未结余额，不新增 journal_entries，因此不会重复计入费用。

已入账记录作废时保留原 POST，新增 REVERSAL 冲减。原债务未结部分停止生效，已付款部分生成反向退款债务；已有结清记录不重写。更正申请独立审核后产生新的费用和债务。例如团队已报销 200 元，更正为 180 元后，保留 200 元反向应退与新 180 元应付，净额为成员应退团队 20 元，不强行合并历史现金流。

### 2.5 本次明确采用的候选规则

| 对应设计候选 | 实验三选择 |
| --- | --- |
| DD-01 成员与退出 | 创建者初始为 OWNER；可有多名 OWNER，至少保留一名；邀请须接受；退出前检查未完成参与和未结债务 |
| DD-02 流转 | 申请人登记付款、确认使用、退款核平；普通管理员禁止自审；OWNER 仍须显式确认 |
| DD-03 金额、版本、重试 | 整数分、记录版本与内容版本分开、请求编号与内容摘要配对；不承诺任意未来清理后的重试识别 |
| DD-04 分摊结算 | 按 ID 分配余分；一个实际付款主体；管理员登记线下结清 |
| DD-05 更正 | 原记录作废加冲减，创建独立更正申请；已结款通过反向债务调整 |
| DD-06/07 保留 | 不在 A/B 中擅自选择，清理关闭；本实现仍有保留政策验收缺口 |
| DD-08 预算 | 按业务日期归属月/年，已完成费用占用预算；未完成申请不占正式预算，超额不阻断 |

另有一个保守边界：已付款申请若要修改，先登记全额退款到账并核平，再修改、重审和重新登记付款。本版本不处理部分退款，也不覆盖原付款事实来伪装改价。

## 8. 尚未完成的范围与后续改进

1. **数据保留未通过最终验收。** 仅金额永久保留与历史分类、年度预算、未结债务的依赖存在冲突；当前保存演示数据并关闭清理，必须先确认永久结构与期限再实现清理和恢复过滤。
2. **桌面程序不提供联网协作。** 四角色和 200 成员是在同一本地数据库的逻辑身份，不是已部署的多人在线服务器。后续可在保留服务层的基础上接回 Web/API 与 PostgreSQL。
3. **附件和付款模型有限。** 仅支持报价链接、单个实际付款主体和全额退款，不支持附件上传或多人分次垫付。系统不执行在线转账，不声称能自动确认实际到账。
4. **备份与性能是局部验证。** 已实现手动备份接口并验证恢复后金额，未实现定时备份、自动恢复或候选性能阈值。
5. **本地安全边界有限。** 应用内重新鉴权不能阻止拥有数据库文件权限的人直接改文件；进程内 Session 也不是远程认证令牌。后续生产化需要重新设计认证与部署边界。
6. **人工审核仍需本人完成。** 自动测试覆盖的是已写入测试的行为，不保证覆盖所有财务场景；提交前应逐行审核并实际操作系统。
